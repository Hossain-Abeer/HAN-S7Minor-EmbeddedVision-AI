D.1 GREP VS AST - WHEN EACH IS CORRECT
  Grep for "import requests" in a source tree finds:
    - Actual imports.           <-- what you want
    - String literals containing that text.   <-- false positive
    - Comments containing that text.          <-- false positive
    - Docstrings containing that text.        <-- false positive

  AST (abstract syntax tree) parses the file into a structured tree.
  Only nodes of type ast.Import or ast.ImportFrom are import
  statements. A string literal is ast.Constant. A comment is not in
  the AST at all (stripped by the parser). A docstring is ast.Constant.

  Consequence:
    - grep returns 9 hits on deploy_test.py itself because the file
      contains the string "import requests" in its own source.
    - AST returns 0 hits because no file in src/ actually imports
      requests (or any banned module).

  RULE: for "no X dependency" claims, scan the AST, not the text.
  Same principle applies to taint analysis (data flow, not string
  matching) and security audits (semgrep, bandit — all use AST or
  bytecode). Grep is a hint. AST is a proof.

D.2 WHY REPRO = 0.0000 AND TR7 = 0.00e+00 ARE DIFFERENT TESTS
  Both are "0.00" numbers. They test different failure modes.

  TR7 (Δproba = 0.00e+00 on 5 probe rows):
    - Compares loaded joblib vs in-memory rebuild of the same pipeline.
    - Proves: persistence round-trips without corruption.
    - Catches: joblib write failure, pickle incompatibility, version
      drift, disk corruption, incomplete serialisation.
    - Does NOT catch: a broken deploy wrapper that preprocesses wrong.

  REPRO (batch macro-F1 delta = 0.0000):
    - Compares deploy path (predict.py -> predict_crop) vs sealed
      test result (3.2 evaluate_test.py path).
    - Proves: preprocessing chain (crop -> mask -> features -> vector)
      produces the same inputs the model was trained on.
    - Catches: feature order mismatch, mask threshold drift, missing
      feature, wrong scaler application in wrapper.
    - Does NOT catch: joblib corruption (would be caught by TR7).

  Two tests, two failure modes. Both are needed.

D.3 WHY FR5 NEEDED AST AND FR6 DID NOT
  FR5 (no network imports): the claim is "no X exists anywhere in
  source". This is a code property, not a runtime property. Needs
  static analysis over the AST.

  FR6 (reproducible split): the claim is "running the code again
  produces the same output". This is a runtime property. Needs an
  actual re-run + output hash comparison.

  Static vs dynamic verification is a fundamental distinction:
    - Static: inspect the code, the structure, the imports.
      Cheap. Does not require execution. Catches structural violations.
    - Dynamic: execute and observe. More expensive. Catches
      behavioural violations that static analysis cannot see.

  Section 7 should reflect this: FR5 is a static proof, FR6 is a
  dynamic proof, and both are appropriate for their claim.

D.4 WHAT MAKES A "PASS" MEANINGFUL IN A RUBRIC CONTEXT
  A row that says "PASS" is only meaningful when:
    1. The measured value is explicit ("78.2 ms", "0.00e+00").
    2. The target is explicit ("<= 1000 ms", "< 1e-9").
    3. The measurement method is explicit (in the test_plan.md).
    4. Failure routes to a documented limitation (Section 8), not
       silent retry.

  deploy_results.csv satisfies 1-3. The routing discipline (no re-tune,
  no re-split, no second prediction pass) was established at 3.2 and
  preserved here: any FAIL becomes a Section 8 entry, not a fix.

  Contrast: a report that says "deploy tested, all good" without a
  table is unverifiable. A table with 15 explicit measurements is
  auditable. The rubric criterion "Test plan present, results
  documented" is satisfied at the artefact level, not at the prose
  level.

D.5 WHY FR4 (REJECT PATH) MATTERS FOR THE S7 PARENT PROJECT
  The OCR subcomponent sits inside the S7 project. The S7 project
  shows the camera frame to the classifier, but many crops will NOT
  be legible numerals:
    - Cue ball (no numeral).
    - Ball at edge of frame (partial ball).
    - Ball under occlusion (another ball on top).
    - Motion blur (ball moving).

  If the classifier returns a confident label on these crops, the
  parent project will mis-attribute rules (e.g. thinks cue ball is
  ball 15). Catastrophic downstream.

  FR4 provides the safe default: return None, not a guess. The parent
  project then knows to try again next frame instead of acting on
  garbage.

  Section 7 should state this explicitly: "FR4 is a safety requirement
  for the parent project. Predictions on non-numeral crops are
  rejected with label=None, allowing the parent to skip those frames
  rather than act on a confident-but-wrong label."
