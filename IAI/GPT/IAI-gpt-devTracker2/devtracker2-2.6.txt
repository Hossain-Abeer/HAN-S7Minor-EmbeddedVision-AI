A.2 PURPOSE
  Decision step, not a scoring step. Takes 3 candidates from 2.4/2.5,
  applies a formal ranking rule, emits ONE selected model name + a
  written rationale + a JSON artefact that downstream steps (3.1, 3.2)
  consume.

  The report needs exactly one model carried forward. Rubric requires
  "select best model, argued" - a defensible rule, not just "we picked
  the highest number".

A.3 THREE-LAYER RANKING DESIGN
  Layer 1 - Primary : CV macro-F1 from grid search (2.4 mean_test_score).
            In-distribution; unbiased; heaviest weight.

  Layer 2 - Corroboration : Val rank preservation from 2.5.
            Confirms or challenges primary ordering.
            NOT an absolute score (val is distribution-shifted, L16).
            Its VALUE is the ordering, not the magnitude.

  Layer 3 - Tie-break : applies ONLY if primary top-2 gap < noise floor.
            Ordered rules:
              a. fewer val per-class F1 zeros
              b. higher val min_class_f1
              c. lower model complexity (knn=1 < svc=2 < rf=3)

  Override clause : MANUAL_OVERRIDE + OVERRIDE_REASON.
            Only mechanism to deviate from mechanical tie-break.
            Must be documented in the note.

A.4 NOISE FLOOR
  NOISE_FLOOR = 0.087 (max baseline CV std from 2.2: rf 0.0865 -> 0.087).
  Any CV gap below this triggers the tie-break chain.
  Rationale: fold-to-fold swing of 0.087 is indistinguishable from noise
  at 245 rows / 5 folds. Gaps smaller than this are not evidence.

B.3 CORROBORATION
  Val ordering rf > svc > knn MATCHES CV ordering exactly.

  This is the strongest single signal in 2.6: the ranking is
  stable across two very different data conditions
  (in-distribution CV, shifted val).

B.4 WHAT THE TIE-BREAK DID
  Rule a (zeros): all 3 = 6 zeros -> no differentiation.
                  Val is too shifted to expose model-specific
                  differences in zero-F1 classes. Expected.
  Rule b (min_f1): all 3 = 0.0000  -> no differentiation.
                  Same cause.
  Rule c (complexity): knn=1 < svc=2 < rf=3 -> knn wins.

  Mechanical winner: knn.
  This is the design's intended behaviour given the inputs.
  It is not a defect. It is the rule chain doing exactly what
  it was designed to do.

B.5 WHY RULE C'S WINNER IS WRONG HERE
  Rule c is designed for the case where models are genuinely
  EQUIVALENT - i.e. equally good, so prefer simpler.
  That precondition is false here:
    - knn CV F1 is 0.06 BELOW rf. Not equivalent; ordered.
    - knn val F1 is 0.036 BELOW rf. Not equivalent; ordered.
  The "equivalent" reading was an artefact of the wide noise
  band (~0.087) caused by thin data (245 rows, 5 folds of ~49).
  Wide noise band = wide confidence intervals, not equivalence.
  When point estimates are ordered inside a wide band, the
  ordering is still a signal; treating it as noise discards
  genuine information.

B.6 WHY THE OVERRIDE TO RF IS DEFENSIBLE
  Three arguments, priority order:
    (1) RF is #1 on CV F1 (0.7193, best of 3).
        Primary metric. In-distribution. Unbiased.
    (2) RF is #1 on val F1 (0.3425, best of 3).
        Corroboration. RF survives the clip-5 shift better than
        svc or knn - resilience under distribution shift.
    (3) RF is default-robust.
        Grid search found NO meaningful tuning gain for rf
        (delta +0.0002 = pure noise, 2.4 C.3).
        This is not a weakness. It means rf at defaults is
        already near-optimal for this data. At deployment, fewer
        knobs means fewer failure modes.

B.7 WHY NOT SVC (RUNNER-UP)
  SVC tuned F1 = 0.7027. Close to rf. But:
    SVC BASELINE F1 = 0.6023.
    Tuning gain = +0.1004.
    SVC's good score is ENTIRELY dependent on C=100 being correct.
    C=1  -> 0.6023
    C=10 -> 0.6619
    C=100-> 0.7027
  Sensitivity to C is ~0.10 across the grid. That is fragile.
  Deployment: every small data change could swing SVC's score by
  up to 0.10. Default-robust beats tuned-fragile for a project
  where the model will be tested once, honestly, on 119 samples.

B.8 WHY NOT KNN (MECHANICAL WINNER)
  KNN trails rf on BOTH metrics:
    CV F1  0.6576 vs 0.7193  (knn is 0.062 below)
    Val F1 0.3061 vs 0.3425  (knn is 0.036 below)
  Rule c promoted the WORST model to the top on complexity
  grounds. That inversion is the direct evidence that rule c
  should never fire when the val signal is unreliable.
  Precondition for rule c (equivalent primary scores) was not
  met, so rule c's output was not a valid selection.

B.9 RANK PRESERVATION AS THE KEY INSIGHT
  Even under a ~0.36 macro-F1 drop on val (2.5 B.1), the model
  ORDERING is preserved.
  Interpretation: RF's advantage over svc/knn is not a CV
  artefact. It holds when inputs change distribution. That is
  the strongest single piece of evidence for the RF selection.
  If rank preservation had failed (e.g. val order svc > rf > knn),
  the selection decision would have been genuinely contested and
  should have been flagged as an open question in Section 6.
  It did not fail. Rank preservation is a legitimate
  corroboration signal, distinct from val's absolute scores.

C - TEACHING - TIE-BREAK CHAIN AND OVERRIDE
--------------------------------------------------------------------------------

C.1 WHAT THE NOISE FLOOR IS AND IS NOT
  IS : a threshold for "we cannot distinguish scores below this".
       Derived empirically from fold-to-fold CV std (2.2).
       Consistent with the actual behaviour of the data.
  IS NOT : a claim that differences below it are MEANINGLESS.
            Differences below it are not STATISTICALLY ROBUST at
            this sample size. They are still POINT-ESTIMATE
            ORDERINGS, which is exactly what we have.

C.2 WHY WIDE NOISE FLOOR HERE
  245 training rows / 5 folds = ~49 rows per fold.
  Thin classes (C5, C10 = 5 samples) are sparsely represented
  across folds. One fold losing both C10 samples swings the mean
  by 0.05+. Thin data = wide noise. Not a defect; a sample-size
  reality.

C.3 THE THREE TIE-BREAK RULES IN THEIR ORIGINAL DESIGN
  Rule a. "If one model handles thin classes better, prefer it."
          Rationale: bad on thin classes = bad in deployment
          (real pool games have all 15 balls present).
          Evidence source: val per-class F1 zeros.
  Rule b. "Higher min_class_f1 = better worst-case behaviour."
          Rationale: deployment cares about the worst class,
          not the average.
          Evidence source: val per-class F1.
  Rule c. "Lower complexity = fewer failure modes."
          Rationale: when genuinely tied on performance,
          prefer the simpler system.

  The chain is ordered a -> b -> c. Each rule narrows the
  candidate set; if one candidate remains, tie-break halts.

C.4 WHAT WENT WRONG IN THE CHAIN HERE
  Rules a and b both depend on val being a representative
  secondary signal.
  L16 (2.5) established val is distribution-shifted. Rules a
  and b are dead.
  Rule c fired without rule a or b having properly narrowed
  the candidate set. Rule c then decided on complexity alone -
  which selected the weakest candidate.

C.5 THE OVERRIDE PRINCIPLE
  When a mechanical rule produces a result that violates the
  rule's own precondition, the rule's output is INVALID.
  The correct behaviour is: fall back to the primary signal
  (CV ordering), document the fallback, and record the
  rationale.

  This is not "fudging the result". This is "the rule was
  applied outside its design envelope; correction is required".
  The override is explicit, is in the code, is in the note,
  is in the JSON, and is in this devtracker. Nothing hidden.

C.6 WHAT MAKES AN OVERRIDE LEGITIMATE VS ILLEGITIMATE
  LEGITIMATE:
    - Explicitly declared in code (MANUAL_OVERRIDE variable).
    - Rationale paragraph is required (OVERRIDE_REASON).
    - Recorded in note + JSON + devtracker.
    - Justified by evidence outside the mechanical rule.
    - Does not contradict the primary metric.

  ILLEGITIMATE:
    - Silent - just changing the output without a trail.
    - Contradicts the primary metric with no justification.
    - Applied to a clear-cut decision (not a tie).
    - Applied to save a failing result (post-test retuning).

  This override is legitimate on all five criteria:
    - Declared (MANUAL_OVERRIDE = "rf").
    - Rationale present (OVERRIDE_REASON paragraph).
    - Recorded in all 3 artefacts.
    - Justified by rank preservation + default robustness,
      which are independent of the tie-break rules.
    - CV F1 also favours rf, so override does not contradict
      primary metric - it honours it.

C.7 WHAT THE OVERRIDE REVEALS (design finding, not fix)
  The tie-break chain implicitly assumed val is a reliable
  secondary signal. It is not, in this project (L16).
  Consequence: rules a and b became inert, rule c decided
  unilaterally, and rule c picked the weakest model.
  Better design (for future work):
    - Detect unreliable val before running tie-break.
    - Fall back to CV ordering, not complexity, when val is
      unreliable.
    - Restrict rule c to cases where CV ties at the top of the
      ranking, not cases where all candidates are inside the
      noise band.

C.8 REPORTING LANGUAGE FOR SECTION 6
  "The tie-break chain was designed to prefer simpler models
  when CV scores were indistinguishable. However, the val
  signal at 2.5 revealed a distribution shift (clip 5, ~2x
  crop scale), which rendered the val-based tie-break rules
  (a, b) unusable. Rule c (lower complexity) then mechanically
  selected k-NN, which scored lowest on both CV and val F1.
  A documented override selected RF on three grounds:
    (i) highest CV macro-F1,
    (ii) highest val macro-F1 despite shift,
    (iii) default-robust tuning behaviour.
  This override and its rationale are recorded in
  models/2.6_selected_model.json."

C.9 REPORTING LANGUAGE FOR SECTION 8 (LIMITATIONS)
  "The tie-break rule chain used val metrics (rules a, b) that
  became invalid due to the distribution shift. Under
  noise-band ties, the tie-break fell to complexity preference,
  which selected the weakest model. Future work should
  (i) check val distribution assumptions before relying on
  val in selection, and (ii) fall back to CV-only ranking when
  val is unreliable."

D - DETAILED TEACHING - EVERY FOUNDATIONAL CONCEPT TOUCHED
--------------------------------------------------------------------------------

D.1 WHAT IS A "MODEL SELECTION" DECISION
  Given N trained candidate models, pick exactly one to carry
  forward to finalisation and test. Selection is a decision,
  not a computation. It combines:
    - quantitative evidence (CV scores, val scores, statistics)
    - qualitative evidence (sensitivity, complexity, robustness)
    - judgement (when the quantitative evidence is inconclusive)

D.2 WHY THE PRIMARY METRIC IS CV, NOT VAL
  CV trains and scores within the training distribution.
  It is the CLEANEST measurement of generalisation quality
  available on this dataset, because train rows come from
  clips 2-4 (consistent scale) and folds are random subsets
  of that consistent pool.

  Val measures generalisation to new data. It is a purer test
  of "works on unseen data" - BUT ONLY IF val comes from the
  same distribution as train. In this project, val (clip 5)
  does not (L16). Val's absolute score is therefore not a
  valid measure of model quality. Its RANK is still useful,
  because rank preservation is a weaker assumption than
  score preservation.

D.3 WHY RANK PRESERVATION IS WEAKER THAN SCORE PRESERVATION
  Score preservation: model achieves same macro-F1 on val as
    on CV. Strong assumption. Requires val = train distribution.
  Rank preservation: model's ORDERING relative to other
    models is preserved across data conditions. Weaker
    assumption. Requires only that models' relative robustness
    is consistent - which follows from architectural differences
    (RF bagging vs SVC kernel vs kNN distance) being stable
    across distributions.

  Implication: even when val scores are garbage, val ranks can
  still be used as corroboration. This is what 2.6 did.

D.4 WHAT "DEFAULT-ROBUST" MEANS
  Default-robust: model's performance is insensitive to
  hyperparameter choice within a reasonable grid.
  Default-fragile: model's performance varies a lot with
  hyperparameter choice.

  RF : default-robust (grid spread 0.0286, below noise floor).
  SVC: default-fragile (grid spread 0.324, 11x noise floor).
  KNN: moderately sensitive (grid spread 0.265, 9x noise floor).

  Deployment implication: default-robust models are safer
  because they do not depend on having found exactly the right
  hyperparameter. In a one-shot test with 119 samples, SVC's
  C=100 result could be a lucky fold draw; RF's result would
  not be.

D.5 WHY "LOWER COMPLEXITY" IS THE LAST RULE, NOT THE FIRST
  Complexity preference is only valid when performance is
  genuinely equivalent. Making it the first rule would always
  pick the simplest model, regardless of quality.
  Making it the last rule means: use performance evidence
  (rules a, b) to narrow down first; only when performance is
  genuinely tied does simplicity break the tie.

  The design is correct. The behaviour was wrong because
  rules a and b were dead, causing rule c to fire before the
  candidate set was properly narrowed.

D.6 WHAT A "LOCKED HYPERPARAMETER" IS
  A hyperparameter whose value is fixed at selection time and
  never changed during 3.1 or 3.2.
  Locked here: rf with {max_depth=10, min_samples_leaf=1,
  n_estimators=300}.
  Locking prevents post-test retuning (which would be
  dishonest) and prevents accidental divergence between
  3.1 (finalise) and 3.2 (test).

D.7 WHAT THE SELECTED_MODEL.JSON IS FOR
  Downstream steps (3.1, 3.2) read it as the single source of
  truth for "which model, which params".
  3.1 refuses to run if the file is missing.
  3.2 refuses to run if the file does not match the pipeline
  that was built at 3.1.
  This makes the selection traceable and non-silent. A model
  swap would require editing the JSON, which would show in git.

D.8 WHERE EACH NUMBER CAME FROM (audit chain)
  cv_f1   0.7193 : grid_search.py, rf best row, mean_test_score
                    (2.4 grid log, cv_results_rf.csv row 3)
  cv_std  0.0865 : same row, std_test_score
  val_f1  0.3425 : evaluate_val.py, rf row in val_summary.csv
  n_zero  6      : same row, computed from per-class f1_score
  min_f1  0.0    : same row, minimum per-class f1_score
  noise   0.087  : max baseline cv_std from 2.2, rounded

  Every number in the decision table traces to a file. No
