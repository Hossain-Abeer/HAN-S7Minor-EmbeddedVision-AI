SECTION C - TEACHING RECORD
--------------------------------------------------------------------------------

C.1 WHAT predict.py IS
  The deployment wrapper. Training started from a feature CSV; the 3.1
  joblib consumes 15 features, not images. predict.py closes the gap
  by re-running the training-time preprocessing chain (crop -> mask ->
  features -> vector) on raw images and feeding the resulting vector
  into the persisted pipeline.

C.2 WHAT A SMOKE TEST IS
  A minimal end-to-end run on a small batch to prove the plumbing
  works before scaling to full deployment testing. It proves SHAPE
  and ORDER, not ACCURACY.

C.3 WHAT THE 4.1 RUN PROVED
  1. Image -> label chain works without crash.
  2. Feature order is correct (predictions would be garbage if wrong).
  3. Probability outputs are well-formed (sum to 1, non-negative).
  4. The 1<->5 sink reproduces across independent code paths.

C.4 WHAT THE 4.1 RUN DID NOT PROVE
  1. FR4 (reject illegible crops): 0 rejects because all 82 crops
     had usable masks. Reject path is code-verified but not run-verified.
  2. Inference latency (TR5): no timing.
  3. Full test-set reproduction (0.2607): single-class batch, not
     the 119-row test set.

C.5 WHY THE HEADLINE 81.7% ACCURACY IS MISLEADING
  Accuracy on a single-class batch is not model quality. It is
  dominated by whichever class happens to be over-represented in the
  source folder. Here, ~49% of crops come from the training set
  (clips 2-4); those are memorised by construction, so they predict
  at near-certainty. The 81.7% figure is inflated by the train share.
  The honest number on unseen crops (clips 1 + 5) is ~64% on a single-
  class batch. That is the class-1 local accuracy, not macro-F1.

C.6 WHY "SAME PROBABILITY VECTOR ACROSS MULTIPLE ROWS" IS EXPECTED
  RF gives each sample a probability vector based on which leaves it
  falls into across the 300 trees. If multiple training crops fall in
  the same set of leaves (common on 245 rows with 300 trees), they
  receive identical vectors. This is not a reproducibility bug. It
  is the RF ensemble geometry: leaf occupancy is coarse on small data.

C.7 WHY FEATURE ORDER CANNOT BE VERIFIED DIRECTLY FROM CSV
  A wrong feature order does not raise an error. It silently maps
  proj_x_3 to the slot that trained for blob_area_ratio, and every
  prediction is garbage. The only signal is behavioural: predictions
  are below chance (chance = 1/15 = 6.7% per crop). Here, predictions
  align with plausible class-1 signal ~82% of the time. That level
  of plausibility only occurs when feature order is correct.
  For a direct proof, we rely on 3.1's reload check: the loaded
  pipeline is byte-identical to what 3.2 consumed, and 3.2 reproduced
  expected predictions. Inherited verification.

C.8 WHY FR4 MUST BE TESTED SEPARATELY
  FR4 = "reject crops that do not contain a legible numeral."
  The 82 class-1 crops all contain legible numerals. mask_is_usable()
  returns True on all of them, so the reject branch is never executed.
  A reject-path bug (e.g. silently returning a random label instead of
  a reject status) would go undetected.
  Proper test: feed 5+ non-numeral crops (cue ball, blank ball, blurred
  patch). Assert count(status=='mask_unusable') > 0. This is a 4.4
  action item, not a 4.1 re-run.

C.9 WHAT COUNTS AS "SHAPE MISMATCH" AND WHY IT WOULD FAIL LOUDLY
  If the pipeline expected 15 features and predict.py produced 16, or
  if predict.py produced a 1-D array where predict() expected 2-D,
  sklearn would raise ValueError immediately. The absence of that
  error confirms shape correctness. Order correctness is the harder
  property: no error fires, only degraded predictions. B.2's 82%
  accuracy is the proof of order correctness.

C.10 HOW THIS STEP FITS THE DEPLOYMENT STORY
  Section 7 of the Full ML report must describe an end-to-end
  deployment pipeline. 4.1 IS that pipeline. Without 4.1, Section 7
