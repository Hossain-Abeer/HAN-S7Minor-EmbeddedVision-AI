================================================================================

Twenty masks were rendered as thumbnails and inspected visually.
Key observations:

  - Numeral as hole: confirmed across all 20. Every mask shows a
    distinct interior void in the shape of a digit. Even "1" produces
    a narrow slit, and "4" produces the expected triangular void.

  - Cloth rejection: backgrounds are uniformly black. The 15% cloth
    ring added at 1.3.2 is fully masked out by the CLOTH_* intersection.

  - Blob shape: consistently circular/ovoid, matching the white patch
    on the ball. No merged blobs, no half-ball crops in this sample.

  - No specks: the OPEN=1 morphology removed noise. No scattered white
    pixels outside the main blob.

  - Stripe non-leak: not testable in this sample (all class 1 = yellow
    solid). Must be re-verified when 6.3 hits classes 9-15 (striped
    balls have a white stripe band that could potentially leak into
    the mask).

================================================================================
5. SKELETAL EXPLANATION - WITH [PARAMS] & DESCRIPTION
================================================================================

5.1 mask_dry_run.ps1 - wrapper

    # src/mask_dry_run.ps1
    $env:[EVML_DRY_RUN_CROPS] = "[CAP_VALUE]"
    python src/[SCRIPT]
    Remove-Item Env:[EVML_DRY_RUN_CROPS]

    PARAMS:
      [EVML_DRY_RUN_CROPS]  env var name       = "EVML_DRY_RUN_CROPS"
      [CAP_VALUE]           env var value      = "20"
      [SCRIPT]              python entry point = "mask.py"

    DESCRIPTION:
      PowerShell wrapper sets the dry-run environment variable before
      invoking python, then cleans it up on exit. This is the same
      pattern established at Section 3 (extract_dry_run.ps1) for
      consistency: one convention, two dry-run knobs
      (EVML_DRY_RUN_FRAMES for frames, EVML_DRY_RUN_CROPS for crops).

      The wrapper is intentionally placed in src/ alongside the script
      it wraps. It is NOT part of the pipeline; only 6.2 and any future
      tuning session invoke it.

      CAP_VALUE = 20 comes from designtracker-6.2 "Cap to first 20
      crops across 2-3 classes."

      Cleaning up the env var is deliberate: without Remove-Item, the
      variable would leak into subsequent PowerShell commands in the
      same session, causing 6.3 (full run) to be accidentally capped
      at 20 crops unless the shell is restarted.


================================================================================
6. DESIGN DECISIONS - ALL CONFIRMED
================================================================================

(a) Dry-run cap via env var, not CLI argument.
    Rationale: matches 3.1's pattern. The alternative (argparse with
    --dry-run-crops) would diverge from the convention established for
    extract_crop.py.

(b) Cap at 20, not 50 or 100.
    Reference: devtracker-6.2 §Action: "Cap to first 20 crops across
    2-3 classes." 20 is enough to eyeball variation in the mask without
    waiting for the full 505-crop pass.

(c) Cap is a total-crops cap, not a per-class cap.
    Consequence: with sorted() order, the first 20 crops all fall in
    class 1. This limits class coverage in the dry run; 6.3's full run
    exercises all 15 classes and will expose stripe-leak risks that
    this dry run cannot.

(d) Wrapper in PowerShell (.ps1), not Python.
    Rationale: parallel to extract_dry_run.ps1; keeps the Python
    script single-responsibility (mask extraction only, env-var
    read only).

(e) Wrapper deferred from 6.1 to 6.2.
    Rationale: tooling is written immediately before the run step it
    serves. Section 3 followed the same pattern (extract_dry_run.ps1
    written at 3.2, not 3.1).

(f) No modification to mask.py for the dry run.
    Rationale: env-var knob means 6.1's code is the SAME code that
    6.3 will run. No dry-run-only code path, no risk of the two
    diverging.

    -> If both missing, class 10 val becomes a HARD zero cell.

       of 1, but thin).

  Stripe-band leakage:
    Classes 9-15 are striped balls. Their white stripe band may
    survive the high-V / low-S threshold alongside the numeral
    patch, producing a large blob rather than a compact patch.
    -> After 6.3, inspect 3-5 masks from class 9, 10, 11, 15.
    -> If the blob includes a wide stripe, the numerals-as-holes
       assumption may degrade for striped classes. Not a blocker;
       document in Preliminary §3 as a known limitation for
       striped classes if observed.

  Long numerals (10-15):
    Two-digit numerals may produce TWO holes (one per digit) or one
    merged hole (if the "1" in "10" merges with the "0"). 1.5.2's
    hole_count feature was designed around single-digit-hole
    assumptions; two-digit numerals will affect hole_count
    distribution. -> Observe at 6.3 and document in EDA (§8.2).

9. RESCALE / FALLBACK TRIGGERS
================================================================================

- If a future dry run shows EMPTY masks for >50% of samples:
    -> lower MASK_V_MIN (180 -> 150).
    -> inspect 5-10 sample crops in a viewer before committing.

- If a future dry run shows CLOTH LEAKING into masks:
    -> re-sample CLOTH_* from a fresh frame.
    -> update constants.py.
    -> re-run 6.2.

- If a future dry run shows NUMERAL NOT AS A HOLE:
    -> check config.MASK_MORPH_CLOSE = 0 (must be zero; if not, set
       and re-run).

- If a future dry run shows >30% rejects:
    -> inspect the rejected crops in MASK_REJECT_LOG.
    -> determine whether rejection is correct (truly no numeral) or
       over-aggressive (thresholds too tight).
    -> if over-aggressive, tune MASK_V_MIN / MASK_S_MAX and re-run.
