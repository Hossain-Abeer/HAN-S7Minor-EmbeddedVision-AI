PURPOSE
-------
Record the outcome of 7.2 (features.py run) against the 492 masks from 6.3.
The mechanical run succeeded (492 rows, 24 columns, no NaN, projections sum
to 1). But 5 of 23 features are constant zero across every row, for every
class. This note diagnoses why, what it costs, and records the decision to
proceed with the remaining 18 features rather than re-engineer the source
data.

This note SUPERSEDES any earlier implicit assumption that 6.1's mask output
contained usable numeral-as-hole structure. It does not.

================================================================================
2. ROOT CAUSE - TWO COMPOUNDING FAILURES
================================================================================

CAUSE A - SOURCE DATA RESOLUTION
    Original capture:  1080p .mp4
    In-game render:    effective ~720p after downsample in recording
    Per-ball crop:     ~30-50 px wide
    Surviving white:   a few dozen px, often only specular highlights
    Consequence:       numeral strokes are 1-2 px wide; the white patch
                       does not form a solid disk, so numerals never appear
                       as enclosed holes. They appear as notches open to
                       background, which find_holes() correctly rejects.

CAUSE B - THRESHOLD MISMATCH
    MASK_V_MIN = 180, MASK_S_MAX = 60 (from 2.3b, tuned against class 1
    yellow solid crops which have high-V white patches).
    For darker balls (8 black, 9-15 striped with dark colours), the white
    numeral patch itself sits at lower V than 180 in many crops. Only
    specular highlights survive.
    The 6.2 dry run inspected 20 crops, all class 1. The threshold was
    never validated against dark-ball classes before 6.3.

Both causes are independent. Fixing B alone (loosening V_MIN to ~120)
would recover some patch area, but at these resolutions the patch may still
never reach enough contiguous pixels to form a solid disk with enclosed
holes. Source resolution is the deeper problem.

================================================================================
3. FEATURE-BY-FEATURE IMPACT
================================================================================

DEAD FEATURES (5 of 23, constant 0 across all rows)
    hole_count             Was intended: "8 -> 2 holes, 0/6/9 -> 1, rest 0"
                           Impact: catastrophic. The single strongest
                           discriminator is gone. 0, 6, 8, 9 collapse into
                           an undifferentiated "round-ish" mass.
    hole_area_ratio        Was intended: hole size relative to blob
                           Impact: reduces within-class separability of
                           hole-bearing numerals.
    hole_aspect            Was intended: "1 tall-thin, 8 square"
                           Impact: loses primary shape cue for 1.
    hole_centroid_dx       Was intended: numeral offset from patch centre
                           Impact: minor positional cue lost; projections
                           partially compensate.
    hole_centroid_dy       Was intended: same vertically
                           Impact: minor.

ALIVE FEATURES (18 of 23)
    connected_component_count  (1-8, varies; fragments split differently)
    blob_area_ratio            (0.004-0.28, noisy but varies)
    proj_x_0..7, proj_y_0..7   (16 features; the main remaining signal)
    Collectively these describe a coarse silhouette of whatever survived
    thresholding. Enough for thin-vs-wide, top-heavy-vs-bottom-heavy.
    Not enough for fine 15-class OCR.

================================================================================
4. OCR VIABILITY UNDER CURRENT DATA
================================================================================

The 15-class OCR objective is now HARDER than the original design intended.

Most-likely-viable classes:
    Class 1   (thin vertical numeral, 82 samples) - highest expected
              accuracy; distinct single-peak proj_x profile.
    Class 7   (top-heavy horizontal + diagonal) - plausible.
    Class 4   (cross-bar) - plausible.
    Class 11  (two strokes for "11") - distinctive via CC count.

Impossible or near-impossible:
    Classes 6 and 9 - rotation ambiguity (180° = each other) and no
                      hole_count to break the tie. Cannot be separated
                      by silhouette alone.
    Classes 3 and 8 - both right-weighted curves; projections overlap
                      heavily.

Difficult:
    Classes 2 and 5 - similar silhouette shapes at typical rotations.
    Classes 10,12,13,14,15 - depend on whether leading "1" projects
                              distinctly enough; mixed.

Realistic expectation:
    15-class accuracy:   20-40% (well above chance at 6.7%; well below
                         the 90% the design's feature set would have
                         supported on 1080p captures).
    Binary "is class 1?": >80% likely.
    Phase 4 CNN recovery: substantial; CNNs read raw crops, and while
                          the crops are pixel-starved, a CNN can still
                          learn from spatial patterns that hand-crafted
                          silhouettes miss.

The pipeline works. The source data does not support the original design
assumptions. This is a source-data limitation, not a pipeline defect.

================================================================================
5. NOTE ON THE SOURCE-DATA CEILING
================================================================================

Real-life capture from a mid-range smartphone (e.g. 108MP sensor) at
sensible working distance would have given ball crops with ~10-20x more
pixels per numeral. Under that capture regime:
    - white patch would form a solid disk,
    - numeral strokes would be 4-8 px wide,
    - find_holes() would fire,
    - hole_count would separate 8 (2 holes) from 0/6/9 (1 hole) from the
      rest (0 holes),
    - the design premise of 1.5.1 / 1.5.2 would hold.

Screen recording of a billiard graphics app was chosen (per the 1.1 change
note and the pre-3.3 pivot) because physical capture was out of scope
(cost, logistics, HAN constraints). The consequence of that choice is the
ceiling documented here.

================================================================================
6. DECISION - PROCEED WITH 18 FEATURES
================================================================================

We proceed to 7.3 (assemble), 8.x (EDA), 9.x (preprocessing), and Phase 2
(classical ML) with 18 live features. The 5 dead features remain in
features.csv (they will be detected by 8.2 as flat-line features and by
8.3 as zero-mutual-information; that detection is itself a positive EDA
outcome worth documenting).

RECOVERY OPTIONS CONSIDERED

    Option A - Re-run 6.1 with looser thresholds (V_MIN 180 -> 120).
        Cost: ~30 min re-extract + re-verify + re-run 7.1/7.2.
        Expected gain: blob_area_ratio grows, projections sharpen.
        Expected loss: still no enclosed holes at this resolution (patch
        too fragmented to enclose numeral strokes).
        Verdict: modest gain, no fix for the hole_count failure.

    Option B - Re-capture with physical camera (smartphone, 108MP).
        Cost: out of scope.
        Verdict: not viable for this semester.

    Option C - Proceed and document.
        Cost: zero.
        Verdict: SELECTED. Consistent with 4.4's "functional end-to-end
        pipeline over large datasets" and the flexible grading rationale.

    Option D - Scope to binary class-1 classification.
        Cost: redesign 15-class to binary; abandon most work.
        Verdict: not justified; 15-class is still possible.

Note that Option A does not escape the resolution ceiling. It only shifts
the failure mode from "5 dead features" to "5 features with weak but
nonzero signal." Not worth the re-run cost at this stage. If a future
stage (e.g. 8.2 EDA) reveals blob_area_ratio dominance causing 6/9
confusion irrecoverable, revisit as an escalation.

================================================================================
7. FRAMING FOR THE MODULE
================================================================================

This is a pipeline development exercise. The module's assessment (per 4.4,
5.3) is scoped to demonstrating a complete, correct, documented ML pipeline
on a small dataset. It is not scoped to producing a production-grade
billiard OCR module for the end-product system.

The pipeline demonstrated so far:
    ingestion (3.x)        -> 1438 crops, over-produced by motion gate
    sorting (4.2)          -> 513 kept, 925 culled by uniform rule
    audit (4.4)            -> 505 (0.999 kept, per-class distribution)
    split (5.2)            -> 3/1/1 group-by-clip, deterministic
    verify (5.3)           -> 15/15/15 class coverage, 2 soft misses
    mask (6.1-6.3)         -> 492 masks, 13 rejected
    features (7.1-7.2)     -> 492 x 23 features, 5 dead, 18 live

The pipeline works. Each step did what it was designed to do. Where the
data did not support a step's design premise (6.1's mask threshold, and by
extension 7.2's hole_count), the correct response is to document the
limitation, not to blame the pipeline or abandon it.

================================================================================
8. WHAT FEEDS PRELIMINARY ML SECTION 3
================================================================================

    - 5 of 23 features are constant zero (hole_* family).
    - 18 features carry varying signal, dominated by projections.
    - Phase 2 model will train on 18 features.
    - Confusion matrix expected to show heavy confusion among 0/6/8/9 and
      3/8, moderate among 2/5, and clear separation for 1.
    - Phase 4 CNN expected to recover most lost discrimination because it
      reads raw crops, not hand-crafted silhouettes.
    - Root cause: source data resolution ceiling (1080p screen recording
      of a 720p-effective-render app), not a pipeline defect.
    - Recovery paths: physical camera capture (out of scope), looser
      mask threshold (marginal), accept-and-document (selected).
