5. TEACHING CLARIFICATION - LOGICAL SPLIT, NOT PHYSICAL
================================================================================

QUESTION RAISED
    "All 5 clips were combined and sorted into class folders. There
    are no clip1/, clip2/ subfolders. So what does 'val = clip 5' mean
    when the files live in 1/ ... 15/ mixed together?"

ANSWER - THE SPLIT IS LOGICAL, NOT PHYSICAL
    splits.csv is a LOOKUP TABLE, not a file mover.

    On disk, after 4.2:
        unsorted_png/
        ├── 1/
        │   ├── clip1_frame000003_ball1.png
        │   ├── clip2_frame000003_ball1.png
        │   ├── clip3_frame000003_ball1.png
        │   ├── clip4_frame...png
        │   └── clip5_frame000003_ball1.png
        ├── 2/  (same mix of clips)
        ...
        └── 15/ (same mix of clips)

    No subfolder per clip exists. Every class folder holds crops from
    all five clips, mixed.

    splits.csv content (excerpt):
        filename,role
        1/clip1_frame000003_ball1.png,test
        1/clip2_frame000003_ball1.png,train
        1/clip5_frame000003_ball1.png,val
        ...

    The role column is derived from the SOURCE CLIP embedded in each
    filename:
        clip1_...  -> test
        clip2_...  -> train
        clip3_...  -> train
        clip4_...  -> train
        clip5_...  -> val

    "val = clip 5" therefore means: "every crop whose filename starts
    with clip5_ gets role=val in splits.csv". Nothing else. No files
    move.


WHY THIS DESIGN (from 1.4.1 §8)
    Rejected: physically moving files into train/, val/, test/ folders.
      - Duplicates storage across experiments.
      - Renames break provenance (filename encodes origin clip).
      - Re-splitting with a different rule becomes a rewrite.
    Selected: CSV is a logical map. Files stay in their class folders.
    Downstream scripts filter by role at load time.


HOW PHASE 2 USES THIS
    7.3 (assemble.py) joins features.csv + splits.csv into dataset.csv
    with columns: filename | label | role | 23 features.

    Phase 2 training code reads dataset.csv and filters:
        train = df[df["role"] == "train"]
        val   = df[df["role"] == "val"]
        test  = df[df["role"] == "test"]

    The role column does all the work. Files are never relocated.


WHY GROUP-BY-CLIP MATTERS (leakage defence - recap from 1.4.1 §4)
    If the split were file-level random:
        clip1_frame000100_ball0.png -> train
        clip1_frame000105_ball0.png -> val
    These two frames are 5 apart - visually near-identical. A model
    that memorises the train frame will "recognise" the val frame, not
    by learning ball features but by pattern-matching the exact same
    image. Val accuracy is inflated. Real-world generalisation is not.

    Group-by-clip prevents this: all frames of clip 1 play the same
    role. Val never sees a near-duplicate of a train frame. Val
    accuracy becomes an honest estimate of generalisation.

    This is DATA LEAKAGE prevention, and it is the primary reason
    clip-level grouping is used instead of file-level random.


CORRECTED WAY TO STATE THE SPLIT
    "Train on the crops whose role column is 'train'."
    NOT
    "Train on clips 2, 3, 4."

    Both are true, but the first is the operative statement. The
    second describes a consequence of the assignment rule, not a
    physical location.

      documented in Preliminary ML §3 as a known limitation.

      8.1) mitigates the train-side imbalance, not the val/test
      thinness. Acknowledge both separately in the report.
