================================================================================
DATA ACQUISITION PLAN CHANGE - CAMERA TO SCREEN RECORDING
================================================================================

PURPOSE
-------
Document the pivot from real-world camera capture to screen recording of a
billiard graphics game as the data source for the OCR subcomponent, and
enumerate the downstream tracker changes this pivot forces.

--------------------------------------------------------------------------------
1. THE CHANGE IN PLAN
--------------------------------------------------------------------------------

ORIGINAL PLAN (per Project Functional & Technical Reports)
----------------------------------------------------------
- Source: overhead camera mounted above a physical billiard/snooker table.
- Method: live capture of real gameplay.
- Variation axes: angle, distance, lighting, background, table cloth.
- Constraints assumed: fixed camera position, stable illumination, physical
  mounting, repeatable capture protocol.
- Rationale: matches the deployed system's real-world operating conditions.

REVISED PLAN (agreed with IAI module lead, Jeroen)
--------------------------------------------------
- Source: screen recording of a billiard graphics/video game.
- Method: 5 × 1080p .mp4 clips, fixed overhead in-game view.
- Variation axes: reduced to virtual (in-game camera zoom, lighting modes,
  cloth colour if game allows; otherwise held constant).
- Rationale (three reasons):
  (a) Real-world YouTube footage lacked sufficient clarity for numeral OCR
      (motion blur, resolution, occlusion, angle drift).
  (b) HAN would not fund a camera purchase.
  (c) HAN would not fund rental of a physical billiard table.
- Authority: explicit approval from the IAI module instructor.

TRADE-OFFS ACCEPTED
-------------------
- (+) Control: no weather, no lighting drift, no mounting instability, no
  human subjects, no scheduling with a venue.
- (+) Reproducibility: same clip can be re-extracted with different frame
  intervals; same random seed; deterministic dataset.
- (+) Cost: zero hardware spend.
- (-) Domain gap: screen-recorded graphics ≠ real billiard table. Model may
  not generalise to physical deployment without domain adaptation.
- (-) Reduced variance: virtual scenes may not exhibit real-world noise
  (glare, cloth wrinkles, ball wear, camera shake). Augmentation must
  compensate — especially in Phase 4 (DL report).
- (-) Fidelity caveat: ball textures, numeral fonts, and antialiasing differ
  from physical balls. Must be acknowledged in the report.

--------------------------------------------------------------------------------
2. HOW THE CHANGE PROPAGATES THROUGH THE TRACKER
--------------------------------------------------------------------------------

[1.1] ACQUIRE SCREEN RECORDING SAMPLES
---------------------------------------
BEFORE: "Build controlled capture setup: overhead camera, stable lighting,
         fixed distance" with subtasks 1.1.1–1.1.3 (camera, lighting, distance).
AFTER:  Collapsed to a single leaf: acquire 5 × 1080p .mp4 clips under fixed
         environment constants.
IMPACT: Physical-setup subtasks deleted. No camera procurement, no lighting
         rig, no distance calibration. Replaced by environment-constant
         definition (overhead, cloth, ball type) that describes the GAME
         scene, not a physical rig.

[1.2] EXTRACT FRAMES FROM .MP4
-------------------------------
BEFORE: "Capture images of billiard balls with visible numbers. Vary angle,
         distance, lighting, background" with subtasks 1.2.1–1.2.5.
AFTER:  Frame extraction from pre-recorded .mp4 using OpenCV VideoCapture
         at a fixed interval, with filtering for blur and duplicates.
IMPACT: The "vary X" axes no longer apply as live capture instructions.
         Variation is now either (a) inherent in the source clips (if the
         game offers multiple views) or (b) introduced later via
         augmentation (Phase 4). Tracker subtasks shift from physical
         variation to extraction parameters (interval, filter thresholds).

[1.3] CROP BALL REGIONS
------------------------
BEFORE: "Label each ball crop with number (1-15) or cue" with subtasks
         1.3.1 (extract crops) and 1.3.2 (label).
AFTER:  Three-step workflow expanded to five leaves:
         1.3.1 Detect ball regions (Hough / HSV / contours)
         1.3.2 Crop and save candidates
         1.3.3 Create folders 1/ – 15/ (cue optional)
         1.3.4 Sort crops by visible numeral
         1.3.5 Audit class balance (≥N per class)
IMPACT: "Labelling" is reclassified. Numerals on balls are PRE-EXISTING,
         so the task is SORTING / GROUPING, not human labelling. This is a
         semantic correction, not a workflow change — but it clarifies the
         report language and avoids implying manual annotation effort that
         does not exist.

[1.4] SPLIT DATA
-----------------
BEFORE: "Split into train/validation/test, stratified."
AFTER:  Unchanged in form.
IMPACT: Stratification is now easier to guarantee because class membership
         is deterministic after 1.3.5. However, if the extracted dataset is
         small (10 crops/class), stratified splitting across three subsets
         becomes tight — must be flagged as a rescale trigger.

[1.5]–[1.7] FEATURES, EDA, PREPROCESSING
-----------------------------------------
BEFORE: Colour histograms, Hu moments, contour, ORB; EDA; scaling pipeline.
AFTER:  Methodologically unchanged.
IMPACT: Data statistics may differ from real-world captures — e.g. cleaner
         colour distributions, sharper edges, fewer outliers. EDA in 1.6
         will likely show higher feature separability than physical data.
         This is a KNOWN BIAS to document in the report's limitations.

[PHASE 4] AUGMENTATION
-----------------------
BEFORE: Rotation, blur, perspective, lighting, noise — sized for real-world
         variance.
AFTER:  Same operations, but now they CARRY MORE WEIGHT. Virtual captures
         are cleaner, so augmentation is the primary source of realistic
         variance. Rotation, perspective, blur, and brightness jitter
         must simulate physical-world conditions the model will face at
         deployment. This is a stronger argument for aggressive augmentation
         than in the original plan.

[REPORTING - ALL PHASES]
-------------------------
- Preliminary ML report §3 must state the pivot, the rationale, and the
  domain-gap limitation.
- Full ML report §8 (Conclusion) must discuss generalisation gap: virtual
  training data → physical deployment target.
- DL report §3 (Augmentation) must explicitly justify each augmentation
  as domain-bridging rather than routine.
- All reports must credit Jeroen's approval as the source of the pivot.

--------------------------------------------------------------------------------
3. SUMMARY
--------------------------------------------------------------------------------
The pivot simplifies Phase 1 physically (no rig, no camera) and moves the
variance burden downstream into augmentation. Tracker changes are: collapse
of 1.1, rewrite of 1.2 into an extraction task, expansion of 1.3 into
detect/crop/group/audit, unchanged 1.4–1.7, and elevated importance of
Phase 4 augmentation. The main residual risk is the virtual-to-physical
domain gap, which must be carried through every report as a documented
limitation.
