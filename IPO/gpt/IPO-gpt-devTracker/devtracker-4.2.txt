B. CODE CHANGES & ARCHITECTURE
--------------------------------------------------------------------------------
  1. Timestamp Generation (before `while` loop):
     - `timebuf[32]` generated with `strftime(..., "%Y%m%d_%H%M%S", ...)`.
     - `logPath` points to `DATA_ROOT/IPO/logs/4.2-log-consol_out_[timebuf].txt`.
     - `freopen(logPath.c_str(), "w", stdout)` redirects standard output.
     - Terminal goes blank; all `cout` streams go to the file.

  2. Reject Log Alignment (inside `while` loop):
     - Reuses the outer `timebuf`.
     - `rejectPath` becomes `DATA_ROOT/IPO/logs/rejects_[timebuf].txt`.
     - Prevents duplicate variable declarations and ensures 1-to-1 traceability
       between the console log and the rejection log.

  3. Counter Initialization (inside `while` loop):
     - `int nCue = 0, nSolid = 0, nStripe = 0, nUncertain = 0;`
     - Placed *inside* the loop so they reset every frame.

  4. Counter Increments (inside the classification loop):
     - Integrated directly into the `switch (ball.type)` statement.
     - `nCue++`, `nSolid++`, `nStripe++`, `nUncertain++`.

  5. SUMMARY Line (after the classification loop):
     - Format: `SUMMARY frame=X balls=N CUE=A SOLID=B STRIPE=C ?=D fps=F`
     - `balls=N` uses `candidates.size()`.

  D2. The FPS Spike Bug (frame 1320, fps=1274.68):
      - Root Cause: There are two `getTickCount()` blocks.
        (1) The periodic FPS block: `if (frameCount % 30 == 0)`
        (2) The SUMMARY block: calculates instantFps every frame.
      - Collision: When frameCount hits a multiple of 30, both run. Block 1
        sets `prevTick = now`. Block 2 immediately calculates `now - prevTick`
        (~0 ms), resulting in a mathematically huge, but cosmetic, FPS spike.
      - Impact: Cosmetic only. Self-corrects next frame.
      - Fix: Deferred (do not block the pipeline). Document as a known quirk
        for Dev 6.1.

--------------------------------------------------------------------------------
E. TEACHING: THE TWO LOG FILES & FREOPEN
--------------------------------------------------------------------------------
  E1. What is freopen()?
      `freopen(logPath, "w", stdout)` hijacks the `stdout` file pointer.
      Any subsequent `cout <<` is sent directly to the hard drive file.
      Standard output to the terminal is severed.

  E2. The 2 Log Files:
      File A (4.2-log-consol_out_...): 
          - Written by `freopen` (C++ stdout).
          - Contains: Startup info, per-ball features, classifications, SUMMARY.
          - Purpose: System State / Audit trail.
      File B (rejects_...): 
          - Written by `std::ofstream` in `segment.cpp`.
          - Contains: Every dropped contour and why (area, circ, aspect).
          - Purpose: Filter Evidence / Proving false positives are dropped.
      Synergy: The shared timestamp binds them. You can see a frame in File A,
      look at the ball count, and open File B to verify how many shapes were
      rejected to produce that clean count.
