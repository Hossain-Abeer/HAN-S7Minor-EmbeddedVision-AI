--------------------------------------------------------------------------------
C. THE WAY FORWARD (DECISIONS LOCKED)
--------------------------------------------------------------------------------
  Option 1: Gut the reports to only mention ball classification.
  Option 2: Keep the reports, bridge the gap by adding "Rack Detection" to the
            code. 
  
  DECISION: Option 2.
  Rationale: Rack Detection (finding a triangular cluster of ball centers using 
  cv::convexHull and cv::approxPolyDP) is mathematically simple compared to 
  what is already built. It satisfies the Functional Requirements (FR1: Detect 
  start of a new game) and proves the code matches the reports.

  Architecture Decision:
  - Rack Detection will NOT be mixed into the vision pipeline files.
  - It will be a separate module: `src/rack-detection.cpp` and `src/rack-detection.h`.
  - It will consume `vector<BallCandidate>` (from `types.h`) and return a boolean.
  - `main.cpp` acts as the orchestrator, calling vision, then rack-detection.
  - This demonstrates strong software engineering (Single Responsibility Principle).
