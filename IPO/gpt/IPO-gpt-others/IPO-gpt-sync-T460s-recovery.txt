================================================================================
A. SYMPTOM
================================================================================
On Y530, git commands failed repeatedly with:

    error: inflate: data stream error (incorrect header check)
    error: unable to unpack 59194ac9e051dc1ec630eb90d882aebc467b39e9 header
    error: refs/heads/main: invalid sha1 pointer 59194ac...
    error: refs/remotes/origin/HEAD: invalid sha1 pointer 59194ac...
    fatal: loose object 59194ac... is corrupt
    fatal: bad object HEAD

Additional objects later surfaced as corrupt (75daee..., ba446c...,
2d5aa1..., 426a53..., etc.). Git fsck reported invalid reflog entries
and missing reachable objects.

Effect: fetch, push, blame, add, and status all failed. Repo unusable
for any git operation.

================================================================================
B. ROOT CAUSE
================================================================================
Two filesystems, one shared workflow, one of them unsafe for .git.

  Y530        : D:\ (internal)  = NTFS Fixed       — safe for .git
  T460s       : D:\ (USB)       = exFAT Removable  — NOT safe for .git

The USB was used as a live sync medium for BOTH code (repo) and data
(clips). On T460s, git wrote loose objects into .git/objects/ on the
exFAT volume. exFAT:

  - does not record file ownership (git detects this: "dubious ownership")
  - has weaker write semantics for many-small-file workloads
  - is fragile under mid-write disconnects (eject, sleep, unsafe removal)

The result was silent zlib stream corruption in loose objects. Once
an object in the reachable set (HEAD, refs/heads/main, refs/remotes/
origin/*) is corrupt, git stops operating on the whole repository.

Key insight: exFAT corruption is byte-level. Copying the corrupt
object file to NTFS carries the corruption unchanged — NTFS does not
repair zlib headers. Location is not the problem; the bytes are.

================================================================================
G. LESSONS LEARNED
================================================================================
L1. exFAT is a silent corruptor for git workloads. "It works" is
    temporary; failures appear only after accumulated corruption
    reaches a reachable object.

L2. The git error "dubious ownership in repository" was an early
    warning, not noise. It indicated the .git was on a filesystem
    that cannot track ownership. It should have been heeded.

L3. All recovery attempts that copy .git across filesystems fail.
    Corruption is byte-level, not location-level.

L4. Always verify which physical volume a drive letter points to
    BEFORE asserting "D: is safe":
      Get-Volume D | Format-Table DriveLetter, FileSystem, DriveType
    On Y530 D: is internal NTFS. On T460s D: is USB exFAT.
    Same letter, different filesystem, different safety profile.

L5. When local and remote diverge with one clean commit each, rebase
    (not merge, not force-push) is the correct resolution. If the
    local commit contains the superset of remote changes, no
    conflicts occur — the rebase is instantaneous.

L6. Push early, push often. Three unpushed commits (Y530) and three
    unpushed commits (T460s) were the entire operational cost of
    this incident. A `git push` after each devTracker close would
    have made this recovery trivial.
